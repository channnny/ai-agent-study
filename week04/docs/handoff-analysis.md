## 2. 이지현 — 장단점

### 2.1 강점

1. **범위가 넓다** — 4시트(susi_result / susi_eval / jeongsi_result / jeongsi_eval) 전체를 커버. 임지현은 수시 결과만 다룸.
2. **SDD 완성도** — `agent_design.md` §1~§8 + 부록 ABC. 각 단계마다 **수행 주체/입력/처리/성공 기준/검증 방법/실패 시** 6요소 표준화. 신입 엔지니어가 보고 그대로 구현 가능한 수준.
3. **8개 대학 사전 분석 첨부** — `00_통합_발견.md`에 5종 평가요소 표기, 면접 4유형, PK 분기(부산대 케이스), 캠퍼스 매핑이 정리됨. **normalizer-eval 서브에이전트의 도메인 컨텍스트**로 그대로 활용 가능.
4. **정규화 사전 분리** (`normalization-dictionary.md` 9섹션) — 반영교과/등급기준/NULL/숫자/Boolean/전형구분/면접유형/평가표기방식/캠퍼스. 룰 기반 매핑이 LLM 부담 줄이는 구조.
5. **골든셋 평가 체계** — `evaluator` 스킬 + 6시트 리포트(summary, by_university, by_column, missing_rows, extra_rows, mismatched_cells) + DoD 임계치(PK 85%, 셀 90%). 측정 가능한 완료 정의.
6. **스킬 vs 서브에이전트 분리** — Claude Code의 SKILL.md / AGENT.md 패턴 적극 활용. 결정론은 스킬, 판단은 서브에이전트.
7. **실행 가능한 자산 첨부**: `schema_v3.yaml`, `universities.csv`, `2025_어디가입결_통합본.xlsx` (골든셋 21,435행).

### 2.2 약점·누락

1. **W04 "굴러가게만" 목표 대비 과욕** — 4시트 + 8개 대학 + 골든셋 평가 + 200+ 확장 + 서브에이전트 분리까지. 1주차로 보기엔 범위가 크고, 부분 구현 시 측정이 어렵다.
2. **표 파싱 디테일이 추상적** — "BeautifulSoup으로 HTML 파싱 → 4시트 raw DataFrame"이라고만 함. **rowspan/colspan 처리, 그룹 헤더 평면화, forward-fill 같은 실제 어려움은 명세 없음** (임지현 §3.2가 정확히 이 부분).
3. **학년도 의미가 도메인 지식으로만 존재** — `searchSyr=2027 → 2026 평가 + 2025 결과` 매핑은 부록에 있으나, **스키마에 `page_year` vs `result_year` 분리는 없음**. 운영 중 혼동 위험 (임지현이 POC #8로 잡아낸 부분).
4. **빈 산출 가드 약함** — "충진율 ≥ 60%" 같은 임계치는 있으나, `records == 0`이 PASS로 흐를 가능성에 대한 **하드 가드는 명시 없음** (임지현 §3.4의 핵심).
5. **인증/잔액 오류 분류 부재** — "LLM 응답 파싱 실패 → 재시도 → raw_text 보관"까지만. **fatal vs transient 분류, 인증/잔액 오류는 즉시 중단** 같은 운영 정책 없음 (임지현 §3.3 + POC #10).
6. **부트스트랩 모드 부재** — 매핑 사전이 있다고 가정. 사전이 빈 상태에서 시작하는 cold-start 시나리오에 대한 단계화 없음 (임지현 §3.3).
7. **PoC 코드의 검증 결과 부분적** — "가천대 76% PK 매칭"은 언급되나, 어디서 실패했는지, 어떻게 개선해야 하는지 시행착오 기록 없음. handoff README는 "PoC 그대로 사용 금지"라고만.

## 3. 임지현 — 장단점

### 3.1 강점

1. **POC로 검증된 v0.4** — §10에 시행착오 11건 명시. 추측이 아니라 **실측 기반**.
2. **헤더 평면화 명세** — `<thead>` + `<rowspan>/<colspan>` + 숫자 비율 5% 미만 행 = 헤더 식별 + 그룹 헤더 점결합(`학생부등급.70%cut`). 어디가 표가 깨지는 가장 자주 발생하는 지점을 직격.
3. **부트스트랩 ↔ 정상 모드** — 사전 항목 < 20이면 부트스트랩(100% LLM, 첫 5개 강제 REVIEW)으로 시드 확보. 정상 모드 전환 임계 + 자동 통과율 ≥ 70% 함께 명시. **cold-start 문제 해결**.
4. **빈 산출 하드 가드 3종** — records=0, records < raw 행수 30%, admission_type 한쪽만 잡힘 — 셋 중 하나라도 걸리면 무조건 REVIEW. Validator 통과해도 별도 가드.
5. **fatal vs transient 에러 분류** — `429`/`5xx`/네트워크는 지수 백오프 (1s→4s→16s), **`AuthenticationError`/`PermissionDeniedError`/`NotFoundError`는 즉시 전체 중단**. POC #10에서 SDK가 잔액 부족을 AuthenticationError로 분류한다는 실측 반영.
6. **대학 단위 게이트** — 한 대학의 LLM 실패율 ≥ 70%면 대학 전체 REVIEW 큐로. 한 대학의 부적합이 전체 배치를 망가뜨리지 않게 격리.
7. **학년도 모델 명시 분리** — `page_year`(접근 시점) vs `result_year`(데이터 학년도) 스키마 분리. `page_year`가 입시 전이면 입결 없는 것이 정상이라는 정책 명문화.
8. **`univInfo.do` API 발견** — 대학명 → unvCd 자동 변환. 사용자가 대학명만 입력해도 OK.
9. **비용 추정 구체적** — 부트스트랩 $9/60대학, 정상 $2/60대학 (~25분 / ~20분). 운영 의사결정에 바로 쓸 수 있는 숫자.
10. **REVIEW 시트 컬럼 정의** — `unvCd | univName | 항목 | 웹사이트 표현 | 추정 매핑 | 신뢰도 | 스크린샷 경로 | 결정 | 사람 수정값 | 비고`. 사람 검수가 실제 어떻게 일어나는지 구체.

### 3.2 약점·누락

1. **수시 단일 시트만 다룸** — 정시·평가기준은 범위 외. **3주차 회의의 데이터랩스 발표("어디가 전형별 주요사항 = 산출방식 같이 수집")는 미반영**. 이지현이 다룬 4시트 구조와 비교 시 절반 미만 커버.
2. **스키마 정의가 본문에 있음** — yaml/json으로 분리 안 됨. 이지현은 `schema_v3.yaml`을 별도 입력 파일로 명시. 운영 시 코드와 스키마가 한 파일에 묶여있으면 버전 관리 약해짐.
3. **8개 대학 사전 분석 없음** — 대학별 이질성(가천 비율%/서울 7등급/연세 8등급/제주 점수/경북 정성종합 등)에 대한 도메인 지식 자료 부재. Mapper가 LLM 호출 시 제공할 컨텍스트가 명시되지 않음.
4. **정규화 사전 별도 없음** — 본문 §3.3에 "사전 자동 업데이트" 언급은 있으나, 초기 사전의 내용·예시 없음. 이지현 `normalization-dictionary.md`의 9섹션 같은 구체 사전이 빠짐.
5. **평가/골든셋 비교 체계 없음** — "스폿 체크: 매 회차 무작위 N건 사람 1:1 대조"만. 정량 평가(PK 매칭률, 셀 일치율) 없음. 이지현 `evaluator` + `evaluation_report.xlsx`의 핵심 가치가 비어있음.
6. **DoD(Definition of Done) 약함** — "신뢰도 평균, LLM 실패율" 트래킹 언급만. 이지현의 "PK 매칭률 ≥ 85% / 셀 일치율 ≥ 90% / seed 50% 채움" 같은 측정 가능한 완료 기준 없음.
7. **확장 단계 약함** — 60개 단위 1회 배치 가정. 8개 → 200+로 가는 단계화, 부분 갱신 모드(특정 대학만 재수집)는 가볍게 언급만.
8. **출력이 단일 시트** — `outputs/{unvCd}.xlsx`에 `수시` 시트 1개. 골든셋 양식(2단 헤더, 29컬럼, 그룹 헤더 N1:T1·U1:AC1 병합)에 대한 일치 보장 없음.

## 5. 통합 제안 — W04 구현 시 어떻게 합칠 것인가

W04 목표가 "굴러가게만"이므로, **두 설계서를 그대로 통합하면 과욕**이다. 우선순위 기반으로 **최소 구현(MVP) → 확장 단계** 두 트랙으로 나눈다.

### 5.1 MVP (W04 안에) — 임지현 골격 + 이지현 자산

## 6. 누락 영역 통합 정리

세 사람 어디에도 안 잡힌 부분 (W04~W12 어디선가 다뤄야 함):

1. **로깅·관측 가능성** — 두 설계 모두 콘솔 로그 정도. 구조화 로그(JSON 라인) / 메트릭 / 알림 채널 부재.
2. **테스트** — 단위 테스트, 회귀 테스트 정책 없음. 매핑 사전·평면화 같은 결정론 부분은 테스트 작성 가능한데 명세 없음.
3. **adiga 이용 정책·법적 검토** — 임지현이 "범위 외" 명시. 이지현도 언급 없음. 실제 200+ 대학 배치 실행 전에 한 번 확인 필요.
4. **DB 연동 (W07~W08 계획)** — 두 설계 모두 엑셀까지만. Notion Kick-off에 W08 "DB 입력 자동화" 있는데 두 설계서는 DB 스키마 매핑까지 안 감.
5. **사람 검수 워크플로우** — REVIEW 시트는 양쪽 있으나, **실제 사람이 검수한 결과가 사전에 어떻게 반영되는지**의 사이클 명세는 임지현만 부분적.
6. **재현성·결정성** — LLM 비결정성 흡수는 두 설계 모두 confidence 점수에 의존. 동일 입력 → 동일 출력 보장은 없음. 운영 중 "같은 페이지인데 다른 결과"가 나오면 어떻게 디버깅할지 약함.
7. **PII / 마스킹** — 어디가 데이터는 통계라 거의 없으나, 모집요강 PDF·이미지에는 담당자 연락처·합격 사례가 들어갈 수 있음. 양쪽 다 다루지 않음.
